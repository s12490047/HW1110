# 反思：哪個節點最常出錯？檢查如何往前移？

> 對應作業步驟四。以下全部來自這次實際執行，不是事後想像。

---

## 1. 最常出錯的節點

### 第一名：③ 整理／正規化（來源 → schema 的落地層）

不是圖表，也不是 CSS。真正反覆出錯的是「把網頁上的東西變成可驗證欄位」這一步：

| 錯誤 | 具體發生 | 為什麼難 |
|---|---|---|
| 編碼／BOM | JSON 被 PowerShell 寫成帶 BOM 或控制字元，`ConvertFrom-Json` 直接失敗 | 錯誤訊息指向字元位置，不明確指向「你用了錯的寫入工具」 |
| 簡繁混用 | 交付前掃到 3 處（「於」「徑」誤用簡體字形） | 中文讀起來都通，只有機器掃描才可靠 |
| 單位錯置 | CCU 與 copies 都是「數字」，很容易放進同一個 `value` 欄 | 欄位名稱對了，語意還是可能錯 |
| 重複計分 | FFXIV 初稿只記 3 勝，實際 4 勝 | 同一遊戲跨年度、跨類別，人眼容易漏 |

**根因**：這一層同時處理「人的語言」與「機器的型別」，是整個流程唯一無法完全自動化的地方。

### 第二名：獎項帳本的年度邊界

TGA 2025 的遊戲，BAFTA／DICE／GDC 多在 2026 年頒獎。若照「有得獎就加」的直覺，Clair Obscur 會多出 36 分，Astro Bot 與 Helldivers 2 的 BAFTA 年度也會錯位。這是**規則問題**，不是資料問題。

### 第三名：⑤→⑥ 的 UI 狀態

這輪抓到兩個：

- 勾選比較時重建整個 grid，導致 checkbox 被銷毀、鍵盤焦點掉回 body。
- 375px 時 grid 用 `1fr`，被 560px 的表格撐開，整頁橫向溢出到 857px。

兩者都不影響資料正確性，但會讓「看起來能用」的頁面實際上不能用。

## 2. 把檢查往前移到哪裡？

| 原本在後段才發現 | 移到哪裡 | 具體做法 |
|---|---|---|
| 簡體字出現在成品 | ③ 之後、⑤ 之前 | 交付前用簡體字集掃描 `src/`，這次掃出 3 處 |
| JSON 壞掉 | ③ 寫入時 | 一律 UTF-8 無 BOM；Python `utf-8-sig` 讀取；`json.load` 先驗 |
| 獎項加總不對 | ④ build gate | `awardIndex == Σ breakdown`，不符就 exit 1 |
| 來源 ID 打錯 | ④ build gate | 檢查每個 `sources` 都存在於 `sources.json` |
| 年度混算 | 資料層 | 每個獎項都帶 event 年份；2026 資料標 supplement |
| 手機溢出 | ⑥ 但量化 | 每次改版面都量 `scrollWidth` 與 `innerWidth`，不靠肉眼 |
| 焦點丢失 | ⑥ 但量化 | 互動後檢查 `document.activeElement` 是否仍是同一個控制項 |

**核心原則**：能用程式判斷的，全部往前移；不能程式判斷的（例如「Tier 4 不是 20M 銷量」），寫進 caveat、來源卡限制與文件，讓讀者能看到。

## 3. 有沒有因此修改 workflow / graph？

有，改了四次，每次都是「把檢查點往前一格」：

### 修改 1：加入 build gate（④ 從人工變成機器）

原本：資料寫完直接產生 HTML，錯了在畫面上看。
現在：`tools/build.py` 先驗 8 條規則，通過才輸出。這讓 ④ 從「人眼掃描」變成「exit code」。

### 修改 2：獎項從「一句話」變成「帳本」

原本：`awards: "TGA 2022 GOTY, Best RPG..."`。
現在：每個 event／category／result／points 一列，加總必須等於 `awardIndex`。FFXIV 的 18→24 就是這樣被抓到的。

### 修改 3：狀態更新不重建清單

原本：`toggleCompare()` 內呼叫 `renderGameGrid()`。
現在：只呼叫 `syncCompareCheckboxes()`。這條規則適用於所有「勾選、展開、選取」類互動。

### 修改 4：交付前檢查清單（新增 ⑥ 的量化門檻）

- console 必須 0 error。
- 375px 的 `scrollWidth ≤ innerWidth`。
- 互動後焦點不得離開目前控制項。
- 簡體字掃描必須 0 命中。
- build 必須 exit 0 且 token 各出現一次。

## 4. 這次做得好的地方

1. **先 schema、後畫面**：HTML 沒有出現資料檔以外的數字。
2. **缺口被當成發現**：11 款缺 Commercial、5 款 Tier 0，沒有用估算補洞，反而成為「公開數據的形狀決定你看得到哪種成功」的結論。
3. **受阻來源誠實標記**：S21、S22 停在來源卡，沒有把 Wikipedia 轉述偽裝成官方原文。
4. **模擬器公開權重與敏感度**：同一批資料換權重就換冠軍，這件事被寫進畫面，而不是藏起來。

## 5. 這次做得不夠的地方

1. **沒有留存率、ARPU、更新頻率**：所以「長期成功」只能用量化的年數＋主觀支援等級，說服力有限。
2. **亞洲／行動市場的數據缺口最大**：Genshin、HSR、Fortnite 都是 Tier 0，這讓「全球」其實偏西方與 PC。
3. **樣本 18 款，且是目的取樣**：2×2 矩陣的格數很小，任何一格多一款就可能改變敘事。
4. **圖譜沒有時間軸**：看不出「2021 得獎 → 2025 還在營運」的變化。
5. **沒有自動化 QA**：這輪的 console、溢出、焦點都是手動量測，下一次改版仍要重做。

## 6. 如果重做一次

1. **先寫 schema 與 validation，再抓第一筆資料**（這次是反過來，補救成本高）。
2. **獎項 ledger 獨立成表**，每個 event／category／result 一列，直接由程式加總。
3. **每個來源加「可引用欄位／不可引用欄位」**，減少把背景預測放進主表。
4. **把 QA 腳本化**：console、scrollWidth、activeElement、簡體字掃描，一次跑完。
5. **保留 2026 快照為獨立資料集**，不要和 2021–2025 放在同一個欄位裡。

---

## 7. 一句話總結

> 這份專案最常出錯的不是程式，而是**「把話變成欄位」的那一刻**。
> 所以真正的改善不是寫更多程式，而是把檢查從「看到錯再修」移到「寫入前就擋住」。
