# Loop / Graph 設計與實際執行紀錄

> 這一章回答作業的三個問題：**流程長什麼樣、哪些步驟重複、檢查放在哪裡、為什麼。**

---

## 1. 九個節點的循環圖

```
                 ┌──────────────────────────────────────────────┐
                 │                                              │
                 ▼                                              │
  ①取得資料 ──▶ ②查詢 Wiki ──▶ ③整理／正規化 ──▶ ④檢查 ──▶ ⑤產生簡報
                 ▲                 ▲              │            │
                 │                 │              │ 失敗        ▼
                 │                 │              └──────▶ ⑥QA
                 │                 │                           │
                 │                 └────── ⑧分析／建模 ◀── ⑦反思
                 │                                 │         │
                 └────── ⑨圖譜／索引 ◀─────────────┘         │
                                                             │
                          （QA 失敗 → 回 ⑤ 渲染；反思 → 回 ③）┘
```

### 節點定義

| # | 節點 | 輸入 | 輸出 | 失敗長什麼樣 |
|---|---|---|---|---|
| ① | 取得資料 | 來源 URL、問題清單 | 來源卡、原始摘錄 | 403、禁止爬取、頁面改版 |
| ② | 查詢 Wiki | 遊戲名／獎項／指標 | 實體、口徑、已知缺口 | 別名混淆、年度錯位、同名作品 |
| ③ | 整理／正規化 | 摘錄、Wiki 實體 | JSON 欄位、單位、asOf | BOM、簡繁混用、單位錯、重複計分 |
| ④ | 檢查 | JSON、schema、帳本 | 通過／具體錯誤訊息 | 加總不符、缺欄位、來源 ID 不存在 |
| ⑤ | 產生簡報 | 通過檢查的資料 | `index.html` | token 次數錯、渲染未綁定 |
| ⑥ | QA | 產出的 HTML | 通過／缺陷清單 | console error、溢出、焦點丟失 |
| ⑦ | 反思 | 缺陷清單 | 規則修改、檢查點前移 | 只修症狀、不改流程 |
| ⑧ | 分析／建模 | 乾淨資料 | Index、Tier、敏感度 | 把相關當因果、缺值補 0 |
| ⑨ | 圖譜／索引 | 實體與邊 | 72 節點／145 邊 | 孤兒節點、重複邊、方向錯 |

## 2. 哪些步驟會重複？

| 步驟 | 為什麼重複 | 本次實際次數 |
|---|---|---|
| ① 取得資料 | 新來源、403 後換路徑、官方頁面改版 | 每個來源 1–3 次（S21、S22 各失敗 1 次後停止） |
| ② 查詢 Wiki | 同一遊戲多版本、年度歸屬、獎項分類 | 每款案例 2–4 次 |
| ③ 正規化 | 編碼、單位、重複獎項、簡繁 | 每批 2 次以上（JSON 重建 2 次） |
| ④ 檢查 | 每次寫入資料後 | 5 次 build（含 2 次修正後重建） |
| ⑤ 產生簡報 | 每次資料或 src 變更 | 5 次 |
| ⑥ QA | 桌面、手機、鍵盤、互動 | 3 輪（初次、修正後、行動版） |
| ⑦ 反思 | 每個新缺陷 | 3 次（BOM、獎項少計、UI 狀態） |

**不會重複的**：⑧ 分析與 ⑨ 圖譜只在資料穩定後執行一次；它們的輸入必須是「已通過 ④ 的資料」，否則每次資料修正都要重算。

## 3. 檢查點放在哪裡？失敗時往哪裡回？

| 檢查點 | 檢查什麼 | 失敗時 |
|---|---|---|
| 來源卡閘門 | URL、發布日、擷取日、status、限制 | 不讓它進 ingest（S21／S22 就停在這裡） |
| 主張層 | 每個數字是否有 source ID、asOf、口徑 | 標 N/A 或補來源 |
| Schema gate（build） | 31 欄位、Tier 0–5、來源 ID、非負值 | build 直接 exit 1，不產出 HTML |
| 帳本 gate（build） | `awardIndex == Σ breakdown` | 修正 breakdown，不修畫面 |
| 年度 gate | 只收 2021–2025 的獎項；2026 標補充 | 移除該筆或改標 supplement |
| 渲染 gate | 資料綁定、空值、HTML escape、token 次數 | 回 ⑤ 修 render |
| QA gate | console、導航、搜尋、篩選、圖表、graph、模擬器、quiz、375px、鍵盤 | 回 ⑤ 修 UI；若是資料問題則回 ③ |

## 4. 為什麼這樣設計？

1. **最便宜的修正點在最上游。** 一個單位錯誤若進到 JSON，會在卡片、圖表、模擬器、圖譜四個地方各錯一次。
2. **讓機器擋住可機器檢查的錯。** 加總、必填、ID 存在與否、token 次數，全部交給 build，不靠人眼。
3. **人只看機器看不到的錯。** 例如「Tier 4 同時代表 20M 銷量與 500k CCU，這兩者不能等價」——這種語意問題只能寫進 caveat 與文件。
4. **反思要能改規則，不只是改錯字。** 每次缺陷都要回答「下次在哪一步擋住它」。

### 5.3 本輪發現並修正的缺陷

| 缺陷 | 偵測方式 | 原因 | 修正 | 預防 |
|---|---|---|---|---|
| 3 個簡體字（「於」「徑」誤用簡體字形） | 以簡體字集掃描 `src/` | 混用簡繁輸入 | 改為繁體 | 交付前跑繁簡掃描 |
| 比較器勾選後焦點消失 | 連續勾選 3 款，檢查 `document.activeElement` | 每次勾選都重建整個 game grid，checkbox 被銷毀 | 新增 `syncCompareCheckboxes()`，只同步狀態不重建 | 狀態更新不重建清單 |
| 375px 頁面橫向溢出 857px | `document.documentElement.scrollWidth` | grid 軌道用 `1fr`，被 560px 寬的表格撐開 | 改 `minmax(0,1fr)`＋`.grid>*{min-width:0}` | 每次改版面都在 375px 量 scrollWidth |

- **規則圈**：⑦→③ 跑了 1 圈（把「繁簡掃描」與「375px scrollWidth」寫進交付前檢查）。

## 6. 節點之間的資料契約

| 邊 | 契約 |
|---|---|
| ①→② | 來源卡必須有 status；blocked 不得提供數字 |
| ②→③ | 每個數字攜帶 source ID、asOf、口徑 |
| ③→④ | JSON 必須是 UTF-8 無 BOM、id 唯一 |
| ④→⑤ | 只有 build exit 0 的產物可以進 QA |
| ⑤→⑥ | 頁面必須能離線開啟、console 無錯誤 |
| ⑥→⑦ | 缺陷必須記錄「偵測方式」，否則無法前移檢查 |
| ⑦→③ | 反思只能改規則或資料，不能只改畫面 |
