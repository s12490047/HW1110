Deliverable 4 · Data Analysis

獎項 × 市場：四個觀察，沒有一個是因果

如果把「得獎」和「賣得好」畫成散點圖，會看到同向的例子，也會看到反例。這正是為什麼本 Wiki 不做單一成功分數，而是把獎項、玩家證據、商業數據與長線營運分開。

Observation 01

GOTY 與銷量常同向

BG3 110／20M、Elden Ring 90／30M；但 Astro Bot 94／1.5M 說明獎項與量體不必同步。

Observation 02

服務型遊戲獎項少、壽命長

LoL、Fortnite、WoW 的 Award Index 低或 0，但長線營運與文化影響力遠超單一年度。

Observation 03

平台與商業模式改變量體

Roblox 是平台 127M DAU；Minecraft 300M copies。兩者都不是「單一遊戲營收」。

Observation 04

缺值不是 0

LoL、Fortnite、Genshin、HSR、WoW 的市場軸留白；模擬器會重新分配權重，而不是補 0。

為什麼不給一個「成功分數」？

因為「成功」至少有四種不同問題：作品有沒有被同業肯定？有多少人真的在玩？商業上是否成立？能不能長期營運？

把這四題壓成一個數字，會製造虛假精準。本 Wiki 的做法是：分開展示，必要時才用可調權重做教學模擬，並公開公式、缺值處理與敏感度。

分析結論：獎項與市場有重疊，但沒有穩定的一對一關係。最值得追問的不是「誰最成功」，而是「你用哪一種成功在衡量」。

Interactive Model · Not a Verdict

成功權重模擬器：讓你的假設被看見

四個維度：Critical／Award、Player Reach、Commercial、Long-term。調整權重，看排名如何改變。這不是預測，也不是投資建議；它是一個把「你重視什麼」變成可檢查數字的教學模型。

權重

缺值處理：每個遊戲只在自己可用的維度上重新分配權重。若 Commercial 缺失，該遊戲的分數由其他維度按比例重算，不會補 0。表格的「覆蓋」欄顯示用了幾維。
公式公開、可重算

Score = Σ(wd × sd) / Σwd
只對 available 的 d 求和

維度分數 sd缺值
Critical／Awardmin(100, Award Index / 110 × 100)不缺失；0 分代表本期無大獎訊號
Player ReachTier × 20Tier 0 → 缺失，重新分配
Commerciallog10(copies) / log10(300) × 100無銷量／營收 → 缺失
Long-termmin(70, years/20×70) + support（30／15／0）不缺失；2025 新作可能接近 0
Roblox 的 Commercial 以平台 bookings 計算，僅為教學展示，不能與單一遊戲銷量直接比較。

敏感度：換一組權重，前五名會不會變？

敏感度只用四組預設權重，不是連續掃描。它的用途是提醒你：排名對權重選擇很敏感，尤其是獎項與市場的權重。
Deliverable 6 · Loop / Graph

從資料到簡報：不是直線，是會回頭的圖

真正的工作流不是「抓資料 → 寫簡報」一條線，而是「取得資料 → 查詢 Wiki → 整理 → 檢查 → 產生簡報」的循環。檢查會把錯誤送回上游；QA 會把問題送回渲染；反思會改寫 Wiki 的規則。

哪些步驟會重複？

為什麼這樣設計？ 因為最便宜的修正點在最上游。與其在簡報裡改一個錯字，不如讓 schema 在寫入時就拒絕錯誤的單位；與其在圖表上發現加總不對，不如讓 build 在獎項 breakdown 不等於 Award Index 時直接失敗。

限制、反思與來源追溯

一份好的 Wiki 不是「什麼都知道」，而是「知道自己不知道什麼」。以下是本專案的主要限制，以及這次 loop 最常出錯的節點。

選擇偏差

18 款案例是 purposive sample，不是隨機抽樣；不能推論全體遊戲或全體玩家。

權重是任意的

Award Index 與模擬器權重是教學選擇，不是自然定律；換一組權重，排名會變。

Ordinal 不是基數

Market Tier 0–5 是證據等級，不是全球市場規模；Tier 4 不等於某個固定營收。

平台數據不可混用

Roblox 是平台層級；Steam CCU 只涵蓋 PC；註冊帳號不是活躍玩家。

年度邊界

2025 遊戲的 2026 BAFTA／DICE／GDC 與後續銷量不計入，避免與未完成年度混算。

二手來源

部分獎項與銷量以 Wikipedia 轉述交叉核對；官方頁面 403 時已明確標記。

哪個節點最常出錯？ 不是圖表，也不是 CSS，而是「來源 → schema 的落地層」：編碼、單位、年度、獎項重複計分、平台口徑。這些錯誤一旦進到資料，後面每個畫面都會被污染。第二常錯的是獎項帳本的年度邊界，因為同一個遊戲會跨年度、跨典禮、跨「得獎／入圍」。

如何把檢查往前移？

  1. 來源卡先要求 URL、發布日、擷取日、status、限制；缺一不進 ingest。
  2. 每個數字都要有 source ID；沒有就標 N/A，不寫「據估計」。
  3. schema 用 enum 管單位與口徑；build 驗證 awardIndex＝breakdown 加總。
  4. 年度與 asOf 寫進資料，而不是寫在簡報註解。
  5. 渲染前先跑資料檢查；QA 只負責互動與視覺，不負責抓資料錯。

如果重做，我會改什麼？

  1. 先做 schema 與 validation，再抓資料；不要先寫 HTML。
  2. 把獎項 ledger 做成獨立表，每個 event／category／result 一列。
  3. 為每個來源加「可引用欄位」與「不可引用欄位」，減少誤用。
  4. 用官方 API 抓可重現快照，並記錄抓取時間與參數。
  5. 把 QA 自動化：console、連結、表格加總、手機寬度、鍵盤焦點。

最後一句： 這份 Wiki 的價值不在於告訴你「哪款遊戲最成功」，而在於讓你能夠反駁它：指出哪個權重不合理、哪個口徑被混用、哪個年度不該算。能被打斷的模型，比看起來很準的模型誠實。
